# Azure Database for PostgreSQL Flexible Server Deployment & Management

A comprehensive, production-ready implementation of an isolated relational database engine deployed on Microsoft Azure's global infrastructure. This repository provides documentation, architectural choices, validation telemetry, and the core transactional schemas used to fulfill the end-to-end deployment lifecycle.

---

## 🚀 Step-by-Step Deployment Guide

### Phase 1: Provisioning the Managed Infrastructure
1. **Resource Group Creation:** Initiated a deployment container named `rg-dev-india` scoped exclusively to the **Central India** geography to handle regional resource allocation and credit quotas.
2. **Server Architecture Selection:** Deployed an **Azure Database for PostgreSQL Flexible Server** instances to allow granular controls over server configurations, scaling windows, and networking properties.
3. **Compute and Storage Optimization:** - Selected the **Burstable Tier** (`Standard_B1ms` instance with 1 vCPU and 2 GiB RAM) to balance computational efficiency with budget controls.
   - Configured standard storage tiers initialized at 32 GiB with **Storage Auto-Grow** enabled to prevent out-of-space application crashes.
4. **High Availability Strategy:** Evaluated Zone-Redundant High Availability architectures. Note that for deployment scalability testing, enabling HA zones requires migrating from a Burstable SKU to a dedicated General Purpose compute tier cluster.

### Phase 2: Implementation of Network Security Gates
1. **Network Connectivity Profiles:** Implemented isolated public endpoints backed by managed virtual firewalls rather than deep VNet integration to ease client management tooling.
2. **Endpoint Access Firewalls:** Explicitly whitelisted trusted network addresses by configuring firewall rules to allow traffic from designated administrative workstations.
3. **Data-in-Transit Encryption:** Configured the database parameter engine to require encrypted handshakes. The server's `require_secure_transport` attribute was configured alongside a enforced minimum TLS framework version of **TLS 1.2** to prevent plaintext exploitation of active transport streams.

### Phase 3: Identity & Authentication Infrastructure
1. **Dual-Engine Authentication:** Enabled hybrid credential systems supporting both traditional **PostgreSQL Native Native Authentication** and cloud-native **Microsoft Entra ID Authentication**.
2. **Admin Directory Mapping:** Configured a Microsoft Entra ID administrator identity directly onto the server cluster (`Cloudcleaner`), allowing passwordless, token-based administrative data planes.

### Phase 4: Database Connection & Schema Deployment
1. **Client Handshake Execution:** Connected to the remote cluster instance via Visual Studio Code using an explicit secure TLS layer over the default database networking gateway **Port 5432**.
2. **Relational Schema Definition:** Executed a structured SQL migration script that provisions a relational database map complete with primary keys, cascading foreign key constraints, and performance data configurations.
3. **CRUD Validation Lifecycle:** Verified transactional operational integrity by running a sequence of structural statements testing record Creation (INSERT), Reading (JOIN queries), Updating (modifying pricing points), and Deletion (cascading constraints test).

### Phase 5: Monitoring, Metrics, & Disaster Recovery
1. **Workload Analysis:** Monitored system behavior under relational script execution via Azure Monitor Metrics, plotting real-time **CPU Percent** and **Memory Percent** profiles to benchmark utilization baselines.
2. **Disaster Recovery Auditing:** Validated the continuous log streaming sub-systems inside the **Backup and restore** blade, ensuring automated point-in-time recovery maps (PITR) are retained across a rolling 7-day retention cycle.
